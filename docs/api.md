# agent-inbox API contract

Frozen contract shared by the Worker (`worker/`), the UI (`src/`) and the CLI (`bin/agent-inbox.mjs`). Wire types live in `shared/types.ts`. Change this file first, then the code.

Naming: the **orchestrator** is the single looping session that holds the lease; a **manager** is one session per approved goal. The wire names predate that wording and stay as they are: scope `manager`, `meta/manager` and the `manager` role are the orchestrator's; scope `orchestrator`, the `orchestrator` field, `orchestrators/<ID>` and the `orchestrator` role are managers'. Prose in this file says "orchestrator token" and "manager token" in the new sense; backticked words are the identifiers. A **fleet** is one orchestrator, its managers and their items; several fleets can share a deployment, and each token belongs to one (see "Fleets").

## Endpoint index

Paths are under `/api` (browser or bearer) and `/agent/api` (bearer only). "Decider" means a human with role `decider` or `admin`; "admin" an admin human; "orchestrator" the orchestrator token; "own mgr" a manager token on its own items or doc. Tokens have no role, and every token reads and writes only its own fleet's items, managers and review routines ("Fleets"). Details per endpoint below. Any orchestrator-token write may also carry `X-Lease-Session` to be refused once its session no longer holds the lease (Lease, "Lease-checked writes").

## Base paths and auth

The same router answers under two prefixes:

| Prefix | Who | Edge (Cloudflare Access) | Worker check |
|---|---|---|---|
| `/api/...` | Browser UI (humans) | Access app on the whole host, Allow the owner's email(s) | Valid `Cf-Access-Jwt-Assertion` (verified with jose against `ACCESS_TEAM_DOMAIN` / `ACCESS_AUD`) **or** a valid bearer token |
| `/agent/api/...` | CLI, orchestrator, managers | Second Access app on `/agent`, **Bypass** everyone | Valid bearer token only (`Authorization: Bearer ait_<id>_<secret>`) |
| `/hooks/...` | GitHub webhooks, ntfy action buttons | Bypassed with `/agent` (second Access app covers `/hooks` too) | HMAC signature (see Hooks) |

Every request is authenticated in the Worker, so the API fails closed even if Access is missing. `/agent/api/x` is exactly `/api/x` with the prefix stripped, but rejects requests that carry no bearer token. Any other `/agent/...` path answers a JSON 404 (the SPA is never served under the Access bypass).

The one exception is **`GET /agent/api/health`** (and `HEAD`), which takes no token and has no `/api` twin. It makes one D1 read and answers `200 {"ok": true, "migration": "<newest applied migration file>"}` (`null` before any), or `503 {"ok": false}` when the database can't be read, with `Cache-Control: no-store`. It tells nothing else: no lease, counts or names. The deploy's smoke test checks that `migration` is the newest file in `migrations/` ([deploy.md](deploy.md#deploy-from-a-private-deploy-repo)). Other methods on that path need a token like any `/agent/api` route (401 without one).

**CSRF.** Callers authenticated by Access (or `DEV_NO_ACCESS`) rather than a bearer token must send `Content-Type: application/json` on every method other than `GET`/`HEAD`, bodiless ones included (415 `bad_request` otherwise), and if the request carries an `Origin` header it must equal the Worker's own origin (403 `forbidden`). Bearer callers are exempt.

Locally (`wrangler dev`), `.dev.vars` `DEV_NO_ACCESS=1` makes browser requests act as `DEV_USER_EMAIL` **only** when the request host is `localhost` / `127.0.0.1`.

### Fleets

A **fleet** is one orchestrator, its managers and their items: one project. Several fleets can share a deployment, each with its own orchestrator, and the server keeps each token inside its own fleet. People see every fleet.

- **The default fleet.** Every item, manager doc, review routine and token that names no fleet belongs to the default fleet: everything written before fleets existed, and everything a token without a fleet writes. Storage leaves it unset (no `data.fleet` key; `tokens.fleet` and `review_routines.fleet` NULL); the API spells it `default` where it needs a name. A deployment with only the default fleet behaves exactly as it did before fleets.
- **Named fleets.** Ids match `^[a-z][a-z0-9-]{0,31}$`; `default` is reserved. A token's fleet is stored with it (`tokens.fleet`, migration 0012) and never changes: to move an orchestrator to another fleet, mint a new token. A stored value that isn't a fleet id (or `default`) makes the token 401. `GET /api/me` names it (`fleet`, `default` for the default fleet). An admin mints a token for a registered fleet with `fleet` on `POST /api/tokens` ("Tokens"); a manager token belongs to the fleet that owns its manager id.
- **The fleet registry.** A named fleet exists once it has a `fleets/<id>` doc: `{label?, color?, id_prefix?}` (`Fleet` in `shared/types.ts`; `label` up to 64 characters, `color` `#rrggbb`, `id_prefix` the start of its manager ids, `^[A-Za-z][A-Za-z0-9]{0,7}$`, a convention the server doesn't enforce). `fleets/default` is optional and only labels the default fleet. See "Fleets registry" below for the routes. Fleets are never deleted: tokens, items, manager docs, routines and meta docs name them, and the checks below read the registry before they write, which is only safe because an id once registered stays registered.
- **Unknown fleets are refused.** Wherever a person names a fleet (`?fleet=` or a body `fleet` on the lease, schedule and tick-request routes, `?fleet=` on `GET /api/items` and `/api/changes`, a full meta id `meta/<base>:<fleet>` on `PUT`/`PATCH /api/meta/:id` and the batch `meta.*` ops, an admin's `fleet` on an item or manager doc, and `fleet` when minting a token), a fleet that isn't registered is 400 `bad_request`, so a typo can't start docs nobody reads. `default` always passes. An item or manager doc that already names an unregistered fleet keeps it on writes that leave it unchanged. A token's own fleet isn't checked again: it was when the token was minted.
- **What a token sees.** An orchestrator token reads only its own fleet's items (with their qa threads), manager docs and review routines: in `GET /api/state` (and `archived_total`), `/api/state/delta`, `/api/items`, `/api/orchestrators`, `/api/changes` and `/api/reviews`. People (`/api/people`, `/api/users`) and `meta/*` docs are shared by every fleet, apart from each fleet's own lease, status and hours (next item). A manager token keeps its own narrower view (its own items and doc), inside its fleet.
- **Each fleet's lease, status and hours.** Every fleet has its own lease, its own `meta/manager` (status, digest, tick stamps and tick request) and, if it wants, its own work hours. The default fleet's are `meta/lease`, `meta/manager` and `meta/schedule`, as before fleets; a named fleet's are `meta/lease:<fleet>`, `meta/manager:<fleet>` and `meta/schedule:<fleet>`. A token reaches its own fleet's by the usual calls and bare ids (`/api/lease*`, `GET`/`PUT`/`PATCH /api/meta/manager`, the batch `meta.patch manager`, `POST /api/meta/manager/tick-request`, `/api/schedule`, `meta/schedule`), so the same orchestrator code runs in any fleet; `X-Lease-Session` and a claim's re-take check its own fleet's lease, and a lease's default TTL follows its own fleet's hours. A named fleet without `meta/schedule:<fleet>` uses the deployment's `meta/schedule` (its schedule view says `inherited: true`), and `DELETE /api/schedule` drops its own hours again. The default fleet's schedule is the deployment's, so its orchestrator (or an admin) setting it also moves every fleet that inherits it. A named fleet's token reads its hours with `GET /api/schedule`; `GET /api/meta/schedule` is its own `meta/schedule:<fleet>` doc, 404 while it inherits. A token reads and writes another fleet's `meta/<base>:<fleet>` never (403), naming its own fleet's by its full id is the same as the bare one, and `meta/lease*` is written only through the lease endpoints (400 on `/api/meta`). People name a fleet with `?fleet=<id>` (`default` for the default fleet) or `fleet` in the body, on `/api/lease*`, `/api/schedule` and the tick request (naming two different ones is 400), or with the full meta id; without one they get the default fleet's, as before. A token that names another fleet there is 403. Other `meta/*` ids are shared.
- **What a token changes.** Every item or manager doc a token creates belongs to the token's fleet: the server writes `data.fleet` (no key for the default fleet), whatever the body says, and keeps it on every later token write, so a token can't move a doc. A token's read or write of an item or manager doc of another fleet is 403 `forbidden`, pinned or not: `GET`, `PUT`, `PATCH` and `DELETE /api/items/:id`, its qa, decide, claim, archive and withdraw, `GET`, `PUT`, `PATCH` and `DELETE /api/orchestrators/:id`, and the same writes in a batch. The fleet is checked before `if_version`, so a 409 never carries another fleet's doc as `current` (a manager token's write is likewise 403 before its pin on another manager's item).
- **Manager ids stay global.** `orchestrators/<id>`, `#orch.<id>` links and `tokens.orchestrator` all key on them, so two fleets can't each have an `O3`: the first fleet to create a manager doc owns its id, and another fleet's token writing it is 403. A review routine belongs to the fleet of the token that first wrote it; a token of another fleet reading or reporting it is 403. A live manager token holds its id for its fleet too: another fleet's token creating `orchestrators/<id>` while one exists is 403. Minting follows the same owner (the manager doc's fleet, else the routine's, else the oldest live manager token's for that id; "Tokens"). An admin who moves a manager doc to another fleet should revoke its manager token and mint a new one: a token's fleet never changes, so the old one is refused on its moved doc.
- **People** see and decide every fleet's items, under their role. An admin's `PUT` or `PATCH` of an item or manager doc may set `fleet` (a fleet id, or `default` or `null` for the default fleet), which moves it; a `PUT` that leaves `fleet` out keeps the stored one, as it does `status`. Any other value, or a fleet that isn't registered, is 400. People filter with `?fleet=<id>` on `GET /api/items` and `/api/changes` (`default` for the default fleet). A token's `?fleet=` is ignored: its own fleet is forced. Every person, whatever their role, reads every fleet; no token does (there is no all-fleet token).
- **What changed for existing callers.** (1) An orchestrator token no longer reads and writes everything: only its fleet's items, managers and routines. (2) A token's own `fleet` in a body is ignored. (3) A manager id or routine belongs to the fleet that created it. (4) A named fleet's token's lease, `meta/manager` and schedule are its fleet's own, not the deployment's; a person's calls without a fleet stay on the default fleet's. (5) A person naming a fleet that isn't registered gets 400 where any well-formed id used to be accepted. (6) A manager token minted without `fleet` belongs to the fleet that owns its id, not always the default fleet. With one fleet, none of these changes anything.
- **Rolling back.** A Worker from before fleets ignores `tokens.fleet`, so under it a named fleet's token reads and writes every fleet. Once named-fleet tokens exist, revoke the ones you don't trust with every fleet's data before rolling the Worker back past fleet scoping.

**Roles.** A human's role comes from the `users` table (migration 0005), resolved on every request in this order:

1. Their row's `role`, when an admin saved one (`PUT /api/users/:email`).
2. No saved role, and `ADMIN_EMAILS` (deprecated, comma-separated, case-insensitive; blank counts as unset) lists them: `admin`.
3. No saved role, and no row in the table has role `admin` yet (bootstrap): `admin` when `ADMIN_EMAILS` is unset, `decider` when it is set. This is exactly how a deployment behaved before roles (unset: every human an admin; set: listed humans admins, the rest could do everything but tokens and the schedule).
4. Otherwise `viewer`: someone Access lets in without a saved role can only read.

A row with no role (someone who only saved a name or topic, or was copied from `meta/people` by the migration) resolves like no row. Bootstrap ends the first time an admin changes anything through `PUT /api/users/:email`: an admin who isn't saved as one yet is saved as `admin` in the same transaction, so they keep admin and everyone without a role becomes a viewer. The human principal carries `role`, and `is_admin` (`role == "admin"`) for older clients.

Tokens are `ait_<id>_<secret>` (id: 12 lowercase base32 chars, secret: 32 bytes base64url). D1 stores `sha256(secret)` hex; compare in constant time. `last_used_at` is updated at most once a minute per token.

## Conventions

- JSON in, JSON out, `Content-Type: application/json`, `Cache-Control: no-store`. Body limit 256 KiB (1 MiB for `POST /api/reviews/report`). A body that uses `__proto__`, `constructor` or `prototype` as an object key, at any depth, is 400 `bad_request` before any route or batch op reads it (as values those words are fine).
- Timestamps are ISO 8601 UTC strings generated by the server (`new Date().toISOString()`).
- A document on the wire is `Doc<T>`: `{id, version, data, created_at, updated_at, updated_by}`.
- Ids: `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`. Others → 400.
- Errors: `{error, message, current?, index?}` (`index`: the failing op of a batch) with status 400 `bad_request` · 401 `unauthorized` · 403 `forbidden` · 404 `not_found` · 409 `conflict` / `not_open` / `not_decided` / `lease_held` (body includes `current`: the doc as it is now) / `last_admin` / `endpoint_taken` · 413 `too_large` · 415 `bad_request` (CSRF, above) · 500 `internal` · 503 `unavailable` (a feature whose secret is missing or malformed).
- **Version pins.** Every write to an existing doc accepts `if_version` (integer). When given and it doesn't match the stored version → 409 `conflict` with `current`. Creates may pass `if_version: 0` to mean "must not exist" (409 if it does). The write and the check are one SQL statement (`UPDATE ... WHERE version = ?`), never read-then-write.
- **Lease-checked writes** (opt-in, orchestrator tokens). An orchestrator-token write may carry the caller's lease session in the `X-Lease-Session: <session_id>` header. When it does, the write goes through only while that session holds a fresh lease of the token's fleet (`meta/lease` for the default fleet; "Fleets") (`holder_session_id` equal to the header, `expires_at` in the future); otherwise it is 409 `lease_held` with `current`: the lease doc as it is now (`null` when there is none) and nothing is written. See "Lease" for the details. Without the header nothing changes.
- Every successful write bumps `version` by 1, sets `updated_at` / `updated_by`, and (via triggers) appends a row to the change log.
- The server also stamps `data.updated_at` on item and manager writes when the caller didn't set it, and `data.created_at` on item creates.

## Endpoints

### Session

- `GET /api/me` → `Principal`: `{kind: "human", email, role, is_admin}` (`role`: `admin` | `decider` | `viewer`, see "Roles"), or a token's `{kind: "token", name, scope, orchestrator?, fleet}` (`fleet`: its fleet, `default` for the default fleet; see "Fleets").
- `GET /api/state` → `StateResponse`: every item (all statuses), every manager, `meta/manager`, `meta/lease`, the schedule view (for an orchestrator token, its own fleet's three, and for a manager token its fleet's schedule; for a person, the default fleet's), the current change cursor, `me`, `people` (as `GET /api/people` lists them), `snoozes` (the caller's own, item id → until; see snooze) and `pins` (the caller's own, `"<kind>:<ref>"` → pinned at; see Pins), plus `archived_total` (archived items the caller can see), `archived_more` (whether `items` leaves some out; `false` without the param) and `routines` (every review routine that has written, `[{id, version, last_run_at, result}]`; [reviews.md](reviews.md)). The UI loads this on a first boot (or when a delta asks for a reset; see "State delta" below); after that, when `/api/changes` reports something, it fetches `GET /api/state/delta` instead. Orchestrator tokens get only their own fleet's items, managers and routines, and `archived_total` counts only those ("Fleets"). Manager tokens get only their own items, manager and routine, and `people: []`; `archived_total` counts only their own. Tokens get `snoozes: {}` and `pins: {}`.
  - `fleets` (people only; tokens don't get the field): every fleet by id, `default` always and each registered fleet ("Fleets"), as `{doc, manager, lease, schedule}`: its `fleets/<id>` doc (`null` while it has none, which only `default` can lack), and its own `meta/manager`, `meta/lease` and schedule view, the ones its orchestrator token sees (`schedule` with `inherited: true` while a named fleet uses the deployment's hours). The top-level `manager`, `lease` and `schedule` stay the default fleet's. Optional in `StateResponse`: a Worker from before the registry doesn't send it.
  - `?archived=<n>` (integer 0–1000, else 400): every `open`, `decided` and `processing` item (and any without a status), but only the `n` most recently updated archived ones (by the doc's `updated_at`, ties by `id` descending); the rest page in with `GET /api/items?status=archived&before=…` below. The UI sends `archived=100`. Without the param every item comes, as before (the CLI's `state` and the orchestrator rely on it), ordered by `created_at` then `id`; with it, `items` is in no particular order.

### Items (`collection = items`)

- `GET /api/items?status=open,decided&orchestrator=O3&qa_pending=true&type=decision&assignee=alice@example.com` → `{items: Doc<Item>[]}`. All filters optional; `status` takes a comma list; `assignee` takes an email (any case) or `none` for unassigned items (400 for anything else); `fleet` (people only) takes a fleet id or `default` (400 for anything else). Tokens' `fleet` filter is forced to their own fleet, and manager tokens' `orchestrator` filter to their own, with every param below too.
  - **Pages** (`limit` and/or `before`): `GET /api/items?status=archived&limit=100&before=<updated_at>&before_id=<id>` → `{items, more}`, newest first by the doc's `updated_at`, ties by `id` descending. `limit` 1–200 (default 50); `before` is the last row's doc `updated_at`, passed back verbatim, and `before_id` its `id`: the page starts strictly after that row, so equal timestamps never skip or repeat an item. `before` alone means "updated before that time"; `before_id` needs `before`. `more` is true when another page follows. Without `limit` and `before` the response stays `{items}` in the old order (`created_at`, then `id`). 400 for a bad `limit`, a `before` that isn't an ISO 8601 time, or `before_id` alone.
  - **Search** `q=<text>` (at most 200 characters and 10 words, else 400): every whitespace-separated word must appear, as a literal substring (`%`, `_` and `\` match themselves), in the item's `title`, `summary`, `question`, `decision.note` or `orchestrator`; case-insensitive for ASCII letters. Combines with every filter and with paging; History sends `status=archived&q=…&limit=50` for archived items it hasn't loaded.
- `GET /api/items/:id` → `Doc<Item>` (404 if missing).
- `PUT /api/items/:id` body `{data: Item, if_version?}` → `Doc<Item>`. Create (201) or full replace (200). On create `status` defaults to `open`. Validated: `type` in the enum (default `info`), `title` non-empty string, `status` in the enum, `priority` in the enum if set, `options` array of `{id, label}` if set, `links` / `evidence` arrays of `{label, url}` with http(s) urls if set, `close_on_pr` a boolean if set (see `POST /hooks/github`), `assignee` an email if set (stored trimmed and lowercased; `null` stores no key; a stored value the write leaves unchanged is kept as is, even if it isn't an email), `fleet` a fleet id, `default` or `null` (the last two store no key; a token's own fleet is stamped instead, see "Fleets"). Unknown extra fields are kept.
- `PATCH /api/items/:id` body `{data: Partial<Item>, if_version?}` → `Doc<Item>`. Shallow merge (top-level keys replace; a `null` value deletes the key). 404 if missing. Same validation on the merged result. Reassigning is `{data: {assignee: "<email>"}}`, unassigning `{data: {assignee: null}}`; the UI pins it on the version it shows.
- **Decided items are kept.** A token's `PUT`, `PATCH` or answer `data` (`POST /api/items/:id/qa`; the batch ops too) on an item that is `decided` or `processing` is 409 `decided`, with `current`, when the result would change its `status` or `decision`, unless the body (or the op) has `replace_decided: true` (a boolean; 400 otherwise). The message names who decided it, when, and the choice with its label, so the caller reads it before writing again. A write that carries `status` and `decision` as they are passes (the orchestrator still edits other fields), and so do `claim`, `archive` and every human write. Why: on 10-15 a replace pinned on the just-decided version, 49 s after the decision, wiped it, and the server keeps no old contents. The CLI's flag is `--replace-decided` on `post` and `patch`.
- **`assignee`** routes an item to one human: it picks their ntfy topic and Web Push devices (Hooks) and the UI's Mine filter. It doesn't lock: anyone can still decide, and the first decision wins. Agents set it at post time, the orchestrator when routing, a human from the item page. Manager tokens may set it on their own items. A reassign lands in the change log as an ordinary item update, but the log has no assignee column, so `wait` can't filter on it (no `wait --assignee`).
- `DELETE /api/items/:id?if_version=` → `{ok: true}`. Orchestrator or admin human. Also deletes the item's qa docs and everyone's snoozes and pins on it.
- `POST /api/items/:id/decide` body `{choice, note?, if_version?}` → `Doc<Item>`. The page-side decision, made atomic:
  - Item must be `status == "open"`, else 409 `not_open` with `current`.
  - `if_version` binds the decision to the version the human saw: when the open item is at any other version, 409 `conflict` with `current` and nothing is decided (never retried onto newer content). `not_open` wins when both apply. Without `if_version` it decides whatever is current (the CLI's `decide --no-pin`; plain `decide` reads the item and sends its version); the UI always sends the version it rendered and, on `conflict`, shows the updated item with "This item changed since you opened it — review and decide again" and clears the picked option.
  - `choice == "other"` requires a non-empty `note` (400).
  - A review routine's ask (an item with a `review_pr` object, posted by the runner, [reviews.md](reviews.md)) also takes `choice == "github"`, "Done on GitHub": its human handled it on GitHub themselves, and the routine posts nothing. The page offers it beside Other; it isn't one of the item's `options`, so ntfy's lock-screen buttons never show it. Any other item refuses it (400).
  - `choice` must be one the page offers (`shared/choices.ts`, which the page and the ntfy buttons use too): for an item with `options`, one of their `id`s or `other`; without options (or an empty array), `approve` / `reject` / `other` for a `proposal` and `ack` / `other` for every other type; `accept` / `override` for `auto_decided`. Anything else is 400 `bad_request` naming the valid choices. Checked after the `not_open` and pin checks, so a stale page or link is still 409.
  - Normal item: sets `status: "decided"`, `decision: {choice, note, decided_at: now, by: actor}`, `updated_at`.
  - `auto_decided` item: `choice == "accept"` sets `status: "archived"` (the agent's `decision` stays). `choice == "override"` requires `note`, sets `status: "decided"`, `decision: {choice: "override", note, decided_at, by}`, `override_of: <previous decision.choice, or existing override_of>`.
  - Decisions don't publish to ntfy; the orchestrator learns of them from `/api/changes`.
- `POST /api/items/:id/claim` body `{if_version?}` → `Doc<Item>`. Orchestrator's claim-before-act: `status` `decided` → `processing` atomically (`UPDATE ... WHERE status = 'decided' [AND version = ?]`). 409 `not_decided` (or `conflict` when the pin fails) with `current`. The claim stamps `claimed_at`, and when the orchestrator token sends `X-Lease-Session` (so it holds a fresh lease, "Lease-checked writes"), `claimed_by`: that session id. **Re-taking a stuck item:** the same call on a `processing` item succeeds for an orchestrator token whose `X-Lease-Session` isn't the item's `claimed_by` (or the item has none: claimed before claims were named). That is an item a session that died or lost a takeover left mid-act. `claimed_by` becomes the caller's session, `claimed_at` the time, and `reclaimed_from` the previous `claimed_by` (`null` when there was none). The session named in `claimed_by` gets 409 `not_decided` on its own item, as before, so an item it parked stays parked; so does any call without the header, and a human's (humans name no session). Pin it on the version read, as any claim.
- `POST /api/items/:id/archive` body `{if_version?}` → `Doc<Item>`. Sets `status: "archived"` (from any status) for admin humans and the orchestrator token (403 for deciders and viewers). A manager token may archive too, under the narrower rule below.
- **Archiving your own item** (manager tokens). So an agent no orchestrator runs can close its item after reading the decision. Allowed only when all hold, checked in this order: `if_version` is given (400 otherwise), the item's `orchestrator` is the token's (403), it is `decided` (409 `not_decided` with `current`: an `open` item is the human's to decide, and a `processing` one is the orchestrator's, which claimed it), and its `source` equals the token's manager id and isn't an orchestrator-written source (`manager`, `scout:*`, `sweep:*`) (403). Why this can't fight an orchestrator: an orchestrator claims only items from its own registry's managers (and its own sources), and its claim is pinned on the version it read as `decided`, as the archive is; of a claim and an archive on the same version exactly one lands, and the other gets 409 with `current` and skips the item. The server can't tell a standalone agent's token from an orchestrator-launched manager's (both post `source` = their id), so an orchestrator-launched manager leaves archiving to the orchestrator by convention ([manager.md](manager.md)); if it archives first anyway, the orchestrator's claim gets 409 and it skips an item the manager already acted on. No lease condition: manager tokens can't read the lease, and a teammate's agent beside a running orchestrator needs to archive too.
- `POST /api/items/:id/withdraw` body `{if_version?, note?}` → `Doc<Item>`. The asker takes back an open question that no longer applies (the hold it asked about cleared another way, the work it was blocking was dropped). Sets `status: "archived"` and `decision: {choice: "withdrawn", ended: "withdrawn", note, decided_at: now, by: actor}` (no `note` key without a note; `note` at most 8000 chars, else 400). Admin humans and the orchestrator token withdraw any `open` item (403 for deciders and viewers); a manager token only under the rule below. For every caller the item must be `open`: otherwise 409 `not_open` with `current` (a decided item is the human's answer, which stands; archive it instead). An `auto_decided` item is 400: it carries the agent's own call, which the human accepts or overrides. Checks run in this order: `if_version` (409 `conflict` with `current` when it doesn't match, before anything else, so an unknown id with a pin is a `conflict` with `current: null`), 404, the manager rule, `open`, the source rule, `auto_decided`. No push goes out; the item's lock-screen buttons stop working with the version bump, like after any write.
- **Withdrawing your own item** (manager tokens). Allowed only when all hold, checked in this order: `if_version` is given (400 otherwise), the item's `orchestrator` is the token's (403), it is `open` (409 `not_open` with `current`), and its `source` equals the token's manager id and isn't an orchestrator-written source (`manager`, `scout:*`, `sweep:*`) (403): the same ownership rule as archiving, so an agent takes back only the questions it asked itself. **Racing a human's decide.** The withdraw is pinned on the version the agent read as `open`, and a decide is pinned on the version the human saw; both write `WHERE version = <that version>`, so of the two exactly one lands. The other gets 409: the human's decide `not_open` (the page shows the item already closed), the withdraw `conflict` or `not_open` with `current`. An agent whose withdraw gets 409 reads `current`: `decided` means the human answered first, so it acts on that answer (or archives it) rather than withdrawing again.

- `POST /api/items/:id/snooze` body `{until}` → `{item_id, until}`. **Humans only** (403 for every token), deciders and admins (403 for viewers). The caller hides an open item from **their own** Inbox until `until`. Snoozes are per person: teammates still see the item, and for the API it stays `open` (agents never see snoozes at all).
  - `until`: an ISO 8601 time in the future and at most 30 days away (400 otherwise), stored normalized (`toISOString()`) in the `snoozes` table as the caller's row (`item_id`, lowercased `email`, `until`; migration 0007). Snoozing again moves the time. `null` deletes the caller's row (on any status, and for an item that doesn't exist: a no-op); others' snoozes on the item stay.
  - Setting a time needs the item to exist (404) and be `open` (409 `not_open` with `current`), checked in the same statement as the write.
  - The item doc isn't written: its `version`, `updated_at` and `data` stay as they are, so ntfy lock-screen links and pages pinned on that version keep working. `if_version` is accepted and ignored (pages from before per-person snoozes send it). Not batchable.
  - The write lands in the change log as collection `snoozes`, `doc_id` the item id, actor `human:<email>` (the snoozer), `orchestrator` NULL. `/api/changes` shows those rows only to that same human, so their other devices refetch; other humans and every token, the orchestrator included, never see them (and `wait --human` never wakes on one).
  - `GET /api/state` returns the caller's snoozes still to come as `snoozes: {<item id>: <until>}` (`{}` for tokens). The page treats an `open` item in that map as snoozed: it leaves that person's Inbox list, the badge and tab-title counts and prev/next, and shows in a collapsed "Snoozed" group until the time passes (re-checked every minute) or they unsnooze it. A snoozed item that gets decided is simply decided. ntfy and Web Push ignore snoozes.
  - Deleting an item deletes everyone's snoozes on it. The daily Cron Trigger (`worker/prune.ts`) deletes snoozes whose time has passed or whose item is no longer `open`.
  - Before migration 0007 a snooze lived on the item (`data.snoozed_until` / `data.snoozed_by`). The migration copied each one still in the future on an open item to its snoozer's row and left the fields in place (no version bump); nothing reads them now, and `PUT`, `PATCH` and qa answer `data` (and their batch ops) drop them, from the body and the stored doc alike, so no write can set them.

### Q&A thread (`collection = items/<id>/qa`)

- `GET /api/items/:id/qa` → `{messages: Doc<QaMessage>[]}`, oldest first (by `created_at`, then id).
- `POST /api/items/:id/qa` body `{text, role?, if_version?}` → `{message: Doc<QaMessage>, item: Doc<Item>}`. One `db.batch` (a transaction):
  - Role defaults to `user` for humans, `manager` for orchestrator tokens, `orchestrator` for manager tokens. Humans may only post `user`; orchestrator tokens `manager`; manager tokens `orchestrator`.
  - Inserts the message with id `m-<epoch ms>-<4 random base36>`, `created_at: now`, `by: actor`.
  - `user` question → item gets `qa_pending: true, qa_last_at: now, updated_at: now`. Status never changes.
  - `manager` / `orchestrator` answer → item gets `qa_pending: false, qa_answered_at: now, updated_at: now`. `if_version` pins the item update; on mismatch the whole batch fails → 409 `conflict` with `current` (no message is stored).
  - Optional `data` object in the body (answers only): merged into the item in the same update, for "when the answer changes the briefing". Like every write it bumps the item's `version`, so lock-screen buttons pushed before it stop working (409 `conflict`); the answer's own push carries fresh ones.
  - Text: 1–8000 chars.

### Managers (`collection = orchestrators`)

- `GET /api/orchestrators` → `{orchestrators: Doc<Orchestrator>[]}`.
- `GET /api/orchestrators/:id`, `PUT` (create/replace, `{data, if_version?}`), `PATCH` (merge), `DELETE` — same semantics as items. `data.id` is forced to `:id`, and `data.fleet` follows the items' rule ("Fleets"). `DELETE` also deletes everyone's pins on it.

### Meta (`collection = meta`)

- `GET /api/meta/:id` → `Doc` (404 if missing). Known ids: `manager`, `lease`, `schedule`. `people` is 400 here: the `users` table replaced it (below).
- `PUT` / `PATCH /api/meta/:id` with `{data, if_version?}`. Orchestrator or admin human. `lease` is writable only through the lease endpoints, and `people` not at all (400 here). `schedule` is validated like `PUT /api/schedule`.
- `POST /api/meta/manager/tick-request[?fleet=<id>]` body `{note?, fleet?}` → `Doc<ManagerMeta>`. Sets `tick_requested_at: now`, `tick_requested_note: note || null` (creates `meta/manager` if missing) on the fleet's own `meta/manager` ("Fleets"): a token's own fleet's, or the fleet a person names in `?fleet=` or the body (a fleet id or `default`; two different ones are 400; without one, the default fleet's). Orchestrator, or a decider or admin human.
- A named fleet's token names its own fleet's `manager`, `lease` and `schedule` by those bare ids here too; see "Fleets". On `GET`/`PUT`/`PATCH /api/meta/:id` and the batch `meta.*` ops a fleet's doc is named in its id (`meta/manager:<fleet>`): a `?fleet=`, or a `fleet` in the body or the op, is 400 there.

### Fleets registry (`collection = fleets`)

- `GET /api/fleets` → `{fleets: Doc<Fleet>[]}`, ordered by id. People get every fleet; an orchestrator token its own fleet's doc only (none while it has none); a manager token is 403.
- `GET /api/fleets/:id` → `Doc<Fleet>` (404 if missing). An orchestrator token reading another fleet's is 403, before anything is read; a manager token is 403.
- `PUT /api/fleets/:id` `{data, if_version?}` creates or replaces it (201 on create). Admin humans; an orchestrator token only to create its own fleet's doc while it doesn't exist (403 for another fleet's, and for its own once it exists, before `if_version` is checked).
- `PATCH /api/fleets/:id` `{data, if_version?}` merges (a `null` deletes a field). Admin humans only. 404 if missing.
- `:id` is `default` or a fleet id (`^[a-z][a-z0-9-]{0,31}$`), else 400. `data` may hold only `label` (a string, trimmed, 1–64 characters), `color` (`#rrggbb`, stored lowercase) and `id_prefix` (`^[A-Za-z][A-Za-z0-9]{0,7}$`); any other key or value is 400, and a `null` on `PUT` leaves the field out. There is no `DELETE` ("Fleets": registered ids stay registered), and no batch op.
- The change log records a fleet doc under its own fleet (`fleets/default` under the default fleet), so a fleet's token sees its own doc change in `/api/changes`.

### People and roles (`users` table)

One row per person, keyed by lowercased email: `role` (`admin` | `decider` | `viewer`, or none), and what they set for themselves, `name` and `ntfy_topic`. Others see a name and whether a topic is set, never the topic (on ntfy.sh, knowing a topic is enough to subscribe); not even admins read someone else's topic. Migration 0005 copied the old `meta/people` doc in (names and topics, no roles); the doc stays in D1 but nothing reads or writes it. Writes to `users` land in the change log as collection `users`, doc id the email (manager tokens don't see them), so open pages refresh.

- `GET /api/people` → `{people: Person[]}`, `Person = {email, name?, has_topic}`, every row sorted by email. Human (any role) or orchestrator.
- `GET /api/people/me` → `{email, name?, ntfy_topic?}`. Humans only, any role (403 for tokens).
- `PUT /api/people/me` body `{name?, ntfy_topic?}` → the same shape. Replaces the caller's name and topic: an omitted, `null` or blank field clears it. Never changes a role; clearing both removes a row that has no role (as an empty entry left `meta/people`). `name` up to 100 chars (trimmed); `ntfy_topic` 1–64 of `A-Z a-z 0-9 _ -`. Humans only, any role.
- `GET /api/users` → `UsersResponse`. Admin humans get `{users: [{email, name?, role, role_set, has_row, devices, has_topic, created_at?, updated_at?}], bootstrap}`: `role` is the role in effect (the saved one, or the default when `role_set` is false), `devices` the number of Web Push subscriptions stored for the email, `bootstrap` is true while no admin is saved (see "Roles"). Admins also get an entry with `has_row: false` (and `role_set: false`, `has_topic: false`, no timestamps) for every email that has Web Push subscriptions but no row: anyone Access lets in can enable a device without being added, and this is how an admin sees and removes those devices. Everyone else (deciders, viewers, the orchestrator token) gets `{users: [{email, name?, role}]}`, rows only. Manager tokens: 403. Sorted by email.
- `PUT /api/users/:email` body `{role?, name?}` → the admin entry above; 201 when it added the person, 200 otherwise. Admin humans only (403 for everyone else, tokens included: a leaked orchestrator token can't make anyone an admin). `:email` is lowercased (400 if it isn't an email). Adding someone needs `role`; an omitted field keeps what is saved, and a `null` or blank `name` clears it. Demoting the last saved admin is 409 `last_admin`, checked inside the write. During bootstrap, the caller is saved as `admin` in the same transaction (see "Roles"); demoting yourself then is 409 `last_admin` too.
- `DELETE /api/users/:email` → `{ok: true}`. Admin humans only. Deletes the row (role, name and topic), if there is one, and the email's Web Push subscriptions, in one transaction; someone with devices but no row (`has_row: false`) loses just the devices. 404 only when there was neither a row nor a device; 409 `last_admin` for the last saved admin (their devices stay too). Access still decides who signs in: a removed person it still lets in gets the default role, and can turn on a device again.

### Web Push (humans only)

A device's Web Push subscription belongs to the signed-in human. Every route is 403 `forbidden` for tokens (orchestrator and manager alike), so `/agent/api/push/*` never works.

- `GET /api/push/key` → `{key}`: the VAPID public key (base64url, the 65-byte uncompressed P-256 point) the browser subscribes with as `applicationServerKey`. It is `VAPID_PUBLIC_KEY` when both `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` are set; otherwise a key pair generated on the first call and kept in D1 (`vapid_keys`, migration 0004; no route returns the private half). 503 `unavailable` when only one of the two secrets is set, or either is malformed.
- `POST /api/push/subscribe` body `PushSubscription.toJSON()`, i.e. `{endpoint, expirationTime?, keys: {p256dh, auth}}` → 201 `{ok: true}`. Stores the subscription for the caller's lowercased email. `endpoint` must be an `https` URL of up to 2048 chars, without credentials, on port 443, whose host (lower-cased, trailing dot dropped, and stored that way) is a browser push service: `push.apple.com`, `push.services.mozilla.com`, `notify.windows.com`, `googleapis.com` or `google.com`, or a subdomain of one, plus any host in `PUSH_ENDPOINT_HOSTS` (comma-separated, same matching). `localhost`, single-label names, `.localhost`, `.internal`, `.local`, `.lan`, `.home.arpa` and `.corp` names and IP literals in any spelling are refused even when listed there. `keys.p256dh` must be 65 bytes and `keys.auth` 16 bytes, base64url (padding optional). 400 otherwise. The same person storing an endpoint again updates its keys in place and resets `fail_count` (how a device re-confirms itself). An endpoint already stored for **someone else** is 409 `endpoint_taken` and left as it is: nobody can prove they hold a subscription, so a second account can't take one over. The browser unsubscribes and subscribes again instead, which gets it a new endpoint (Settings → Notifications does that on a shared browser); the old one is deleted when its push service answers 404 or 410.
- `DELETE /api/push/subscribe` body `{endpoint}` → `{ok: true, removed: 0 | 1}`. Removes the caller's own subscription with that endpoint (normalized as above); someone else's is never touched (`removed: 0`).
- `POST /api/push/test` → `{sent, failed, removed}`. Pushes `{title: "Test notification", body, url: "/#settings", tag: "test"}` to the caller's own subscriptions, synchronously, with the same bookkeeping as item pushes (Hooks, "Web Push").

### Pins (humans only)

A pin keeps an item, a manager or a Reviews PR in a "Pinned" group at the top of its own list (the Inbox or History, Team, Reviews' PRs) for the signed-in human. Pins are per person, like snoozes: a row per (human, thing) in the `pins` table (migration 0010), never a doc write, so no `version` moves and nobody else's lists change. Every route is 403 `forbidden` for tokens, and agents never see pins. Any human may pin, viewers included: it changes nothing but their own lists.

- `PUT /api/pins/item/:id`, `PUT /api/pins/orch/:id`, `PUT /api/pins/pr/:routine/:n` (no body) → `PinResponse` `{kind, ref, pinned: true, created_at}`. `kind` is `item`, `orch` or `pr`; `ref` is the id, or `<routine>/<n>` for a PR. The thing must exist (an item in any status, a manager doc, a PR row the routine tracks, gone from its newest report or not), checked in the same statement as the write; 404 `not_found` otherwise. `:n` must be a positive integer (400). Pinning again is a no-op that keeps the first `created_at` (and logs nothing).
- `DELETE` on the same paths → `{kind, ref, pinned: false, created_at: null}`. Removes the caller's own pin; someone else's stays. Unpinning what isn't pinned, or no longer exists, is a no-op.
- The pin follows the thing: a pinned item that gets decided or archived stays pinned (the UI moves it from the Inbox's Pinned group to History's). A pinned PR gone from the newest report stays pinned too; the UI fetches one the routine's list no longer carries with `GET /api/reviews/:routine/prs/:n` and says it dropped out.
- Deleting an item or a manager deletes everyone's pins on it, in the same transaction. The daily Cron Trigger (`worker/prune.ts` `prunePins`, after the reviews prune) deletes pins whose item, manager or PR row is gone (a PR pruned 30 days after it dropped out, a routine deleted, a delete by a Worker from before pins). The UI skips a pin on something it can't find meanwhile.
- Each write lands in the change log as one row, collection `pins`, `doc_id` `<kind>:<ref>`, actor `human:<email>` (the pinner, also for a delete by cascade or cron), `orchestrator` NULL. `/api/changes` and the delta show those rows only to that same human, so their other devices update; other humans and every token never see them.
- `GET /api/state` returns the caller's pins as `pins: {"<kind>:<ref>": <created_at>}` (`{}` for tokens). The UI orders each Pinned group newest pin first; a pinned row isn't also shown in its usual group. Not batchable.

### Lease (`meta/lease`)

Data: `Lease`. `ttl_min` 1–300; when omitted (acquire and renew), `max(25, pickup_interval_min + 15)` from the fleet's schedule (schedule defaults while it is missing), so the lease outlives one pickup interval.

Each fleet has its own lease ("Fleets"): a token's calls act on its own fleet's; a person's on the default fleet's (`meta/lease`), or another one's with `?fleet=<id>` on any of these paths (or `fleet` in the body of acquire, renew and release; two different ones are 400). A token that names another fleet is 403.

- `GET /api/lease` → `{lease: Doc<Lease> | null, expired: boolean, now}`.
- `POST /api/lease/acquire` body `{session_id, title?, url?, ttl_min?, force?: boolean, if_version?}` →
  - missing, expired, or already held by `session_id` → write it (`acquired_at` kept when already held by the same session) → 200 `{lease, acquired: true}`.
  - held by another session and fresh → 409 `lease_held` with `current`, unless `force: true` **and** `if_version` equals the current version (steal: the caller proves it saw the lease it is replacing).
  - All writes pinned on the version read in the same request (insert-if-absent or `UPDATE ... WHERE version = ?`), so two concurrent acquirers can't both win.
- `POST /api/lease/renew` body `{session_id, ttl_min?, if_version?}` → `{lease}`. Must be held by `session_id` (else 409 `lease_held` with `current` → the caller steps down). Updates `heartbeat_at`, `expires_at`.
- `POST /api/lease/release` body `{session_id}` → `{ok: true}`. Deletes it when held by `session_id`; 409 `lease_held` otherwise.

**Lease-checked writes.** The lease endpoints are the only ones that look at `meta/lease` by default: any other write from an orchestrator token lands whether or not its session holds the lease. An orchestrator session that lost a takeover and hasn't renewed since could otherwise claim, relay and archive items alongside the new holder. To guard against that, an orchestrator-token request may send `X-Lease-Session: <session_id>` (1–200 chars; 400 otherwise):

- Checked on every write: any method but `GET`/`HEAD`, outside `/api/lease/*`. That is item `PUT`/`PATCH`/`DELETE`, decide, claim, archive, withdraw and qa; manager `PUT`/`PATCH`/`DELETE`; meta `PUT`/`PATCH` and the tick request; `PUT` and `DELETE /api/schedule`; and `POST /api/batch`, checked once for the whole batch (a 409 here has no `index`: no op was looked at, nothing was written).
- Passes when the token's fleet's lease (`meta/lease` for the default fleet; "Fleets") exists, its `holder_session_id` equals the header, and its `expires_at` is still in the future. Otherwise 409 `lease_held` with `current` = the lease doc (`null` when there is none). An expired lease, even your own, fails: renew it first (renew works on an expired lease you still hold).
- Checked before the route's own rules, so a non-holder's write is 409 even where the route would answer 400 or 404.
- Ignored on reads, on `/api/lease/*` (acquire, renew and release follow their own `session_id` rules, so a session can always take over or renew), and for every caller other than an orchestrator token: humans (the UI never sends it) and manager tokens (which can't read the lease, so they don't get it back in a 409 either).
- Why a header and not a body field: it is about the caller, not the document, so it sits beside `Authorization`. It works the same on bodiless requests (`DELETE ?if_version=`, `claim`, `archive`) and on the batch envelope without a new field in any body or op schema, it can't collide with an item's extra fields (which `PUT` keeps), and a client can attach it to every request in one place (the CLI does, from `--session` / `AGENT_INBOX_SESSION`; docs/cli.md).
- The check is one read of `meta/lease` when the request arrives, not part of the write's transaction: a takeover that lands in the few milliseconds between the check and the write doesn't stop that write. That is the same as the write landing just before the takeover, and the new holder's pinned writes (`if_version`) still see it. What the header stops is the real failure, a session writing minutes after it lost the lease.

### Schedule (`meta/schedule`)

- `GET /api/schedule` → `ScheduleView` (defaults from `DEFAULT_SCHEDULE` while the doc is missing; `computed` from `shared/schedule.ts`). When the stored doc doesn't validate, `schedule` is the defaults, `version` is the stored doc's, and `stored_invalid: true` is set (otherwise the field is absent), so a client that merges into the view before writing it back can tell it would replace the stored zone and hours.
- Per fleet ("Fleets"): a token reads and writes its own fleet's schedule, a person the default fleet's (`meta/schedule`, the deployment's) or another one's with `?fleet=<id>`; a token whose `?fleet=` names another fleet is 403. A named fleet's own hours are `meta/schedule:<fleet>`. While it has none, `GET` answers the deployment's schedule with `inherited: true`, `version: null` (the version of the doc a `PUT` would write) and `inherited_version` (the deployment's doc's version, `null` while it has none, so a client can tell those hours changed), without `stored_invalid`, and the fleet follows the deployment's hours.
- `DELETE /api/schedule?fleet=<id>&if_version=` → `ScheduleView` (now inherited). Admin human or the fleet's orchestrator token. Drops a named fleet's own hours, so it follows the deployment's again; nothing to drop is not an error, unless `if_version` named a version (409 `conflict`, `current: null`). 400 for the default fleet, whose schedule is the deployment's.
- `PUT /api/schedule` body `{schedule: Schedule, if_version?}` → `ScheduleView`. Admin human or orchestrator. Validates `work_hours` (`HH:MM-HH:MM Ddd-Ddd`, start < end), `timezone` (accepted by `Intl.DateTimeFormat`), `pickup_interval_min` one of 1, 2, 3, 4, 5, 6, 10, 12, 15, 20, 30, 60, 120 (`PICKUP_INTERVALS`: divides 60, or one or two hours), `sweep_interval_min` an integer from `pickup_interval_min` to 240.

`computed.cron_utc`: pickup firings every `pickup_interval_min` at minute offset 3 (`3-59/10`; `3` with an hour step for 60/120), over every **UTC hour the window overlaps**, at the zone's **current** offset, days shifted when the window crosses UTC midnight (split into two expressions). When the window or the zone's offset isn't on whole UTC hours (09:30–17:30, `Asia/Kolkata`) the cron is a superset that also fires just outside the window, and `computed.cron_exact` is `false`; it is `true` when every firing is inside the window. **The orchestrator must skip a firing when `computed.in_hours` is false.** `computed.next_pickup_at` is the next firing of that cron that falls inside the window. The cron is a convenience for the orchestrator's CronCreate; it must be recomputed after a DST change.

### State delta (live updates)

- `GET /api/state/delta?since=<cursor>` → `StateDeltaResponse` (`shared/types.ts`): the part of the caller's `GET /api/state` that changed after `cursor` (a `cursor` from `/api/state` or from an earlier delta), so an open page applies a few docs instead of refetching the whole snapshot on every change. `since` is required, an integer ≥ 0 (else 400). A separate path rather than `/api/state?since=`: the response is a different shape (partial, or a reset), and `/api/state` stays the one snapshot the CLI and the orchestrator read.
  - It reads the change log after `since` with `/api/changes`' visibility rules, takes each doc named there once, and returns its current version, all in one D1 batch (one transaction), so `cursor` matches the docs exactly. A typical single-item change at about 2.4k items is ~1.9 KB (~1 KB gzipped) and ~20 D1 rows read, against ~330 KB (~72 KB gzipped) and ~2.6k rows for `/api/state?archived=100` (`test/worker/delta-size.test.ts` prints the numbers).
  - Response: `{cursor, items, orchestrators, deleted, qa_changed, me, manager?, lease?, schedule?, people?, snoozes?, pins?, archived_total?, reviews_changed?, routines?, fleets?}`:
    - `cursor`: pass it back as the next `since`; the same cursor a fresh `/api/state` would report.
    - `items`, `orchestrators`: the current doc of each one that changed, once each.
    - `deleted`: `[{collection: "items" | "orchestrators", id}]`, each gone, or no longer the caller's to see (an item reassigned away from a manager token). An id may be one the caller never held (created and deleted inside the window).
    - `qa_changed`: ids of items whose qa thread changed (a question, an answer, the thread deleted with its item). Threads aren't part of `/api/state`, so neither are their messages here: refetch `GET /api/items/:id/qa` for a thread that is open.
    - `me`: always, the caller as `/api/me` returns them now (a role can change through any `users` row: the first admin saved turns everyone without a role into a viewer).
    - `manager`, `lease`: present when that doc changed, `null` when it was deleted (the caller's fleet's, as in `/api/state`). Never for manager tokens (their `/api/state` has them `null`).
    - `schedule`: the schedule view, as in `/api/state`, when `meta/schedule` or the caller's fleet's own `meta/schedule:<fleet>` changed. Manager tokens get it too.
    - `people`: the whole list, as in `/api/state`, when any `users` row changed. Never for manager tokens.
    - `snoozes`: the caller's whole map (item id → until), as in `/api/state`, when one of their own snoozes changed; `{}` once the last one goes. Only the snoozer's delta has it: other humans and tokens never see a snooze change.
    - `pins`: the caller's whole map (`"<kind>:<ref>"` → pinned at), as in `/api/state`, when one of their own pins changed; `{}` once the last one goes. Only the pinner's delta has it.
    - `archived_total`: recounted when an item may have entered or left the archive (a changed item whose archived-ness differs from what it was at `since`, by its last change at or before `since`; one whose history was pruned; for a manager token, any item change). Otherwise absent: the count is the costliest read here.
    - `archived_more` is never in a delta.
    - `fleets`: people only. When a fleet's registry doc, `meta/manager`, `meta/lease` or own `meta/schedule` changed, its entry (as in `/api/state` `fleets`), keyed by fleet id; when the deployment's `meta/schedule` changed, every fleet's entry (a fleet without hours of its own shows those). Only registered fleets and `default` appear. Each entry present replaces the one held; fleets absent are unchanged (fleets are never deleted).
    - `reviews_changed` and `routines`: when a review routine's data changed (a run started or reported, or an admin deleted the routine), the ids of those routines and the whole `routines` list, as in `/api/state`. Review data itself isn't in `/api/state`: refetch `GET /api/reviews/:routine` for a routine on screen ([reviews.md](reviews.md)). A manager token gets only its own routine.
  - Scope: the same view as `/api/state`. Manager tokens get only their own items and manager doc, the schedule, `me` and their own `archived_total`; besides the rows `/api/changes` shows them, the delta also follows `meta/schedule` (and their fleet's own `meta/schedule:<fleet>`) and later changes to items they had owned (within the retained log), which come back as `deleted` once reassigned. Orchestrator tokens get their own fleet's view; an item or manager doc an admin moved out of their fleet comes back as `deleted` the same way.
  - Reset: `{reset: true}` (status 200) when the change log no longer holds every change after `since` (pruned by the retention cron, see the change feed below), when more than 500 changes came after it, or when `since` is past the newest change (a cursor from another database). The client then fetches `GET /api/state` and carries on from its `cursor`.
  - Merge contract (what a client does with a delta):
    1. `reset` → refetch `/api/state` and replace everything with it.
    2. Drop each `deleted` doc by collection and id, then upsert each doc in `items` and `orchestrators` by id. The delta's copy is the current one; a client that applied a newer write result meanwhile may keep that copy (a higher `version` of a doc with the same `created_at`).
    3. For each optional field, present means replace, `null` included: `manager`, `lease`, `schedule`, `people`, `snoozes`, `pins`, `archived_total`, `routines`. Absent means unchanged. `fleets` replaces entry by entry: each key present replaces that fleet's entry, the others stay (a snapshot without `fleets` can't take a partial one: refetch `/api/state`).
    4. Replace `me`, and set the cursor to `cursor`.
    5. Refetch the open qa thread if its item is in `qa_changed`.
    6. Keep archived items it already held: a delta brings each changed item whatever its status, so the archived window (`?archived=n`) only grows until the next full fetch, like a refetch's merge in `src/lib/archive.ts`. `archived_more` keeps its last full-fetch value.
    After that the client's snapshot equals a fresh `/api/state` (with `?archived`: a superset of its items, every extra one archived), apart from `schedule.computed`, which is computed at read time (the UI recomputes it locally) and an expired snooze, which `/api/state` stops listing without a change (the UI hides it by time anyway). `test/worker/delta.test.ts` checks this over a random run of writes for an admin, two deciders, the orchestrator and a manager token.
  - Polling it is the same as before: wait on `GET /api/changes?since=&wait=` and fetch a delta when it reports something.
  - The UI (`src/store.ts` `sync`, merging with `src/lib/delta.ts` `mergeDelta`, the very function `test/worker/delta.test.ts` checks against the server) fetches a delta from the cursor of the state it holds whenever the feed reports something, and falls back to the full `/api/state?archived=100` on `{reset: true}`, any HTTP error from the delta (a 404 from a server deployed before it, mid-deploy), or a delta it can't merge (a cursor behind the one held, another identity in `me`, a malformed body). It also keeps the last good state in IndexedDB (`src/lib/snapshot.ts`: non-archived items plus the newest 100 archived), renders it at once on the next open, and revalidates it with a delta from its cursor; a 401 on that first call clears it from the screen and the device. Writes from a snapshot not yet revalidated stay bound to what was shown: decide and reassign are always pinned (`if_version`), and a question asked then is pinned too (409 `conflict` with `current` if the item changed); snooze and the tick request change no item content.

### Change feed (wake path)

- `GET /api/changes?since=<seq>&wait=<seconds>&collection=items` → `ChangesResponse`.
  - No `since` → `{cursor: <latest seq>, changes: []}` (bootstrap).
  - Returns changes with `seq > since`, oldest first, at most 500; `cursor` is the last returned seq (or `since` when none).
  - `wait` (seconds, default 0; anything above 25 counts as 25): long-poll. When nothing is new, re-check every 1.5 s until something arrives or `wait` passes, or the client disconnects.
  - `collection` filter optional (`items`, `orchestrators`, `meta`, `qa` = any `items/*/qa`, `reviews`).
  - Review routines log one row per write, collection `reviews`, doc id the routine, `orchestrator` the routine, so the routine's own token sees them ([reviews.md](reviews.md)).
  - Snooze rows (collection `snoozes`) reach only the human who snoozed, and pin rows (collection `pins`) only the human who pinned; other humans and all tokens never get them.
  - Fleets ("Fleets"): each change also records its fleet at write time (`changes.fleet`, migration 0012: an item's or manager doc's `fleet`, a qa message's parent item's, a review routine's, and the fleet a `meta/manager:<fleet>`, `meta/lease:<fleet>` or `meta/schedule:<fleet>` doc names; every other row none). An admin's move of an item or manager doc logs one more row, before the usual one, under the fleet it left (with `status` null), so that fleet's feed wakes and its delta drops the doc. An orchestrator token sees its own fleet's rows plus the deployment-wide ones (`users`, and `meta` rows that name no fleet other than the default fleet's own `meta/manager` and `meta/lease`); for the default fleet that is every row with no fleet, so with one fleet it sees every row, as before. A person's `?fleet=<id>` (or `default`) gives that same view; a token's is ignored.
  - Manager tokens only see changes to their own items, their qa and their manager doc, in their own fleet. Ownership is recorded per change at write time (`changes.orchestrator`, migration 0002: the item's `orchestrator`, the manager doc's id, a qa message's parent item's `orchestrator`), so deletes of its items and qa stay visible and a reassigned item's earlier changes stay in its history (until pruned, below); changes after the reassignment belong to the new manager.
  - Retention: a daily Cron Trigger deletes changes older than 30 days (`CHANGES_RETENTION_DAYS`, at least 7; `worker/prune.ts`). Pruned changes are gone for every caller, manager-scoped history included. The newest change is always kept, so the bootstrap cursor and `/api/state`'s `cursor` never go backwards, and `seq` is never reused. A cursor older than the oldest kept change still works: it gets the kept changes after it, which is enough because the feed only means "something changed, refetch `/api/state`". `GET /api/state/delta` is the one reader that needs every change after its cursor: it answers `{reset: true}` instead.
- Orchestrator wake recipe ([orchestrator.md](orchestrator.md) "Wake path"): `agent-inbox wait --human --cursor-file …` in a Monitor until-loop, which chains these long-polls and returns on any change whose `actor` starts with `human:` (or is `hook:ntfy`).

### Batch (several writes, one transaction)

- `POST /api/batch` body `{ops: Op[]}` (1–50 ops, inside the 256 KiB body limit) → `{results: [...]}`, one entry per op in order, each what that op's own route answers (a `Doc`, or `{message, item}` for `item.qa`).
- An op is `{op, id, ...the route's body}`, i.e. a write you could send alone:

  | `op` | Same as |
  |---|---|
  | `item.put` / `item.patch` | `PUT` / `PATCH /api/items/:id` `{data, if_version?, replace_decided?}` |
  | `item.claim` / `item.archive` | `POST /api/items/:id/claim` / `archive` `{if_version?}` (`if_version` required for a manager token's archive) |
  | `item.withdraw` | `POST /api/items/:id/withdraw` `{if_version?, note?}` (`if_version` required for a manager token) |
  | `item.qa` | `POST /api/items/:id/qa` `{text, role?, data?, if_version?}` (answers, or a human's question) |
  | `orchestrator.put` / `orchestrator.patch` | `PUT` / `PATCH /api/orchestrators/:id` `{data, if_version?}` |
  | `meta.put` / `meta.patch` | `PUT` / `PATCH /api/meta/:id` `{data, if_version?}` (e.g. the `digest` stamp: `{op: "meta.patch", id: "manager", data: {last_pickup, digest?, last_tick?, next_tick}}`) |

  Not batchable: decide, snooze, pins, deletes, the tick request, lease, fleets, people and users, schedule (`/api/schedule`; `meta.*` on `schedule` is, with its admin rule) and tokens. Each doc at most once per batch (400 otherwise).
- **All or nothing.** Every op is validated and authorized exactly as its route would (a manager token can batch only what it could do one op at a time), every `if_version` is checked, then all writes run in one `db.batch` (a transaction) that opens with a guard statement failing the whole batch if any doc changed since it was read. On any failure nothing is written, no change-log rows appear and no ntfy push goes out; the error body adds `index`, the failing op's position (body and scope checks run for every op first, then each op's pin and doc rules in order, so `index` is the first failure in that order): 409 `conflict` (pin) / `not_decided` with that op's `current`, 400 / 403 / 404 as the route would answer. Ops without `if_version` that lose a race are rebuilt from a fresh read, like single writes.
- Side effects run only after the commit, once per op: an ntfy push per created ask (`proposal`, `decision`, `blocker`, `pr_ready`), per reassignment and per answer, as the single routes do.
- `X-Lease-Session` (see "Lease-checked writes") is checked once for the whole batch, before any op: a non-holder's batch is 409 `lease_held` without `index`, and nothing is written.
- Cost: one read query, then one `db.batch` of `ops + 1` statements (plus one per `item.qa`).

### Tokens (admin humans only)

- `GET /api/tokens` → `{tokens: TokenInfo[]}`.
- `GET /api/tokens` lists each token's `fleet` too (`default` for the default fleet).
- `POST /api/tokens` body `{name, scope, orchestrator?, fleet?}` → 201 `{token: TokenInfo, secret: "ait_<id>_<secret>"}` (the only time the secret is shown). `scope` is `manager` or `orchestrator`; `orchestrator` (an id) is required with the latter. `fleet` ("Fleets") is `default` or a registered fleet id (400 for any other value, or one that isn't registered):
  - An orchestrator token (`scope: "manager"`) belongs to `fleet`, the default fleet without one.
  - A manager token (`scope: "orchestrator"`) belongs to the fleet that owns its manager id: the fleet of `orchestrators/<id>` if it exists, else of review routine `<id>`, else of the oldest live manager token for `<id>`. Without `fleet` (or with `null`) it takes that owner's fleet, the default fleet when the id has no owner yet. A `fleet` that differs from the owner's, `default` included, is 409 `conflict` ("Manager O3 belongs to fleet fa"), nothing stored. Create the manager doc (or mint in the fleet you mean) first, so the token lands in the right fleet.
  - The owner, the fleet's registration and the name rule below are checked in the same statement as the insert, so concurrent mints can't land a manager id in two fleets. 409 `conflict` (no `current`, nothing stored) when a live (unrevoked) token already has that `name`: the change log records token writes as `token:<name>`, so live names must tell tokens apart. Names compare exactly (case-sensitive, as the actor does); a revoked token's name is free again. The check and the insert are one statement (`INSERT ... SELECT ... WHERE NOT EXISTS`), so concurrent creates can't both take a name. There is deliberately no unique index: nothing enforced this before, so an existing database may already hold live duplicates, which a `CREATE UNIQUE INDEX` migration would fail on. Revoke one of each such pair to make the history unambiguous from then on.
- `DELETE /api/tokens/:id` → `{ok: true}` (sets `revoked_at`; 404 for an unknown id).
- Bootstrap without the UI: `node scripts/create-token.mjs --name manager --scope manager [--fleet <id>] [--remote]` inserts a token with `wrangler d1 execute` and prints the secret once. It runs the very statement `POST /api/tokens` does (`shared/mint-sql.mjs`), with the same name, fleet and owner rules: on a refusal it stores nothing, prints no secret, says why and exits 1. `--create-fleet` (only with a named `--fleet`) also registers that fleet with an empty `fleets/<id>` doc when it has none, and only if the token was stored, for a deployment set up without the UI.

## Hooks

### `POST /hooks/github`

GitHub webhook (content type JSON), verified with `X-Hub-Signature-256` = HMAC-SHA256(`GITHUB_WEBHOOK_SECRET`, raw body). 401 on mismatch; 503 when the secret isn't set. Handles:

- `pull_request` `closed` → `pr_state: merged` (if `merged`) or `closed`.
- `pull_request_review` `submitted` → `pr_state: approved | changes_requested | commented` (from `review.state`).
- `pull_request` `synchronize`, `reopened`, `converted_to_draft` and `ready_for_review` → no `pr_state`; they only update review routines' PRs (below).
- Anything else → 202 `{ignored: true}`.

Review routines: each of these deliveries (closed and submitted reviews included) also merges its facts into the `gh` column of every routine's `review_prs` row for the PR url, bumping each changed routine's head in the same batch, so each logs one change row. Merged and closed set `gone_at` there, and a reopen after a close clears it. The rules are in [reviews.md](reviews.md#github-hook).

Matching: every item whose `links` or `evidence` contains the PR's `html_url` (exact match, also matching `.../pull/<n>/...` sub-pages), and every manager whose `pr.url` is that url (trailing slashes ignored on both sides). The lookup is an index search on the `doc_links` table (migration 0008), so a delivery reads only the docs it matches, archived ones included, however long History grows. Items get `pr_state`; managers get `pr.state`. Two kinds of matching item that is still `open` are also closed, in the same write: a `pr_ready` item when the PR merges, and any item posted with `close_on_pr: true` (other than an `auto_decided` one, whose decision is the agent's) when the PR merges or closes. Each becomes `status: "archived"` with `decision: {choice: "merged", ended: "merged", note: "Merged on GitHub", decided_at, by: "hook:github"}` on a merge, or `{choice: "closed", ended: "closed", note: "Closed on GitHub without merging", decided_at, by: "hook:github"}` on a close without one (`decided_at` is the write's time). Nothing else closes an item: reviews only set `pr_state`, and an item that is already `decided` or `processing` keeps the human's decision and gets only `pr_state` (its asker or the orchestrator archives it). `close_on_pr` is for an item whose question is about its PR (a review hold: once the PR is merged or closed, the question is moot); the flag is the item's content, so set it when posting. Closing with the PR ends the question as a withdraw does, so it has the same owner. The hook decides from exactly these item fields, `CLOSURE_FIELDS` in `worker/hooks/github.ts`: `close_on_pr`, `links`, `evidence`, `type`, `status`, `pr_state` and `decision`. On an existing item it didn't post with `source` = its id, a manager token can change none of them (403 `forbidden`, whichever write: `PUT`, `PATCH`, an answer's `data`, a batch op), and it can create an item with `close_on_pr` only with `source` = its id. Otherwise it could flag an orchestrator's question and link a PR it controls, retype a flagged item in or out of `auto_decided`, or write `pr_state: merged` ahead of the webhook. The orchestrator and admins change them on any item. Closing is decided on the delivery, not on `pr_state`: an open item that qualifies is closed by a signed merge or close whatever `pr_state` already says, and `pr_state` itself still only advances (merged stays merged). A delivery that neither moves `pr_state` nor closes anything leaves the item untouched. `merged` and `closed` are terminal: a later review, or a replayed or out-of-order delivery, leaves them (and the doc) untouched; only `closed` → `merged` goes through (a reopen in between, which the hook doesn't track). Actor `hook:github`. Response `{updated: [{collection, id}]}`: the docs that changed, plus `{collection: "reviews", id: <routine>}` for each review routine whose PRs changed.

### ntfy push (optional, off until a topic is set)

When an item is **created** with type `proposal`, `decision`, `blocker` or `pr_ready`, or a `manager`/`orchestrator` answer is posted (on any item), the Worker publishes (in `ctx.waitUntil`) to `${NTFY_SERVER || "https://ntfy.sh"}/`, once per topic, with `topic` in the JSON body. Topics: the item's assignee's `ntfy_topic` when they set one; otherwise (unassigned, or an assignee without a topic, unknown or a viewer) every person's topic plus `NTFY_TOPIC`, deduped. Viewers' topics are never used: the signed decide buttons work for whoever taps them, so pushes go only to people whose role can decide. Without any topics that is `NTFY_TOPIC` alone; with no topic at all nothing is sent. Reassigning an open `proposal`/`decision`/`blocker`/`pr_ready` (`PUT` or `PATCH` that changes `assignee`) also pushes it, titled `Assigned to you: <title>`, to the new assignee's own topic only: not when they have no topic or are a viewer, and not when the caller assigned it to themselves. Each is ntfy's JSON publish (`Authorization: Bearer NTFY_TOKEN` when set) of the same message, signed links included, with title, the question/title as message, a `view` action to `${PUBLIC_URL}/#item.<id>`, and — for items whose options are known (explicit `options`, or the proposal defaults approve/reject) and at most 2 of them plus the recommendation first — `http` actions `POST ${PUBLIC_URL}/hooks/ntfy/decide?item=<id>&choice=<opt>&exp=<unix>&created=<doc created_at>&ver=<doc version>&sig=<hex>` where `sig = HMAC-SHA256(NTFY_ACTION_SECRET, "<id>|<choice>|<exp>|<created>|<ver>")`, expiring after 7 days. `created` is the item doc's `created_at`, so a link can't act on a later item that reuses the id. `ver` is the doc `version` the push describes: the created doc for a create, the doc the reassign wrote for a reassign push, and the item after the answer for an answer push (answer pushes carry decide actions too, built the same way, when the item is still an `open` `proposal`, `decision`, `blocker` or `pr_ready`). So a tap decides exactly what was pushed: **any later write to the item** (an edit, a question or answer, a reassign, a GitHub `pr_state` update) retires the buttons pushed before it, and the human opens the item instead. Decide actions are only sent for items that are `open`. Without `NTFY_ACTION_SECRET` only the view action is sent.

### Web Push (optional, off until someone enables a device)

Alongside ntfy, never instead of it: the same three events push to the devices in `push_subscriptions` (Settings → Notifications), each in its own `ctx.waitUntil`, never failing the request. Routing follows the ntfy topics, except that viewers' devices are included (a Web Push has no decide buttons): an item's assignee's subscriptions when they have at least one; otherwise (unassigned, or an assignee with no device) every subscription. Reassigning an open ask pushes `Assigned to you: <title>` to the new assignee's devices only, under the same conditions as ntfy (not when they have none, not when the caller assigned it to themselves).

| Event | `title` | `body` |
|---|---|---|
| Item created with type `proposal`, `decision`, `blocker` or `pr_ready` | the item's title | its `question`, else its title |
| `manager`/`orchestrator` answer on any item | `Answer: <title>` | the answer text |
| Reassign (above) | `Assigned to you: <title>` | its `question`, else its title |

The payload is JSON `{title, body, url: "/#item.<id>", tag: "<id>"}`: title cut to 120 chars, body to 600, and both shortened further until the JSON is at most 3000 bytes. It is encrypted to each device with RFC 8291 (`Content-Encoding: aes128gcm`, one 4096-byte record) and sent with a VAPID (RFC 8292) `Authorization: vapid t=<ES256 JWT>, k=<public key>` (`aud` = the endpoint's origin, `exp` = 12 h, `sub` = `VAPID_SUBJECT`, else `PUBLIC_URL`), `TTL: 86400` and `Urgency: high` for `priority: high` items (`normal` otherwise). There are no decide buttons: a tap opens the item (the service worker focuses an open window or opens one at `url`).

Bookkeeping per subscription: a 2xx sets `last_ok_at` and resets `fail_count`; 404 or 410 (the push service says the subscription is gone) deletes it, and so does a 403 whose body says the subscription was made with a different VAPID key (Apple's `VapidPkHashMismatch`, FCM's "does not correspond to the sender ID"); any other status (other 403s included: those are this server's VAPID setup, not the device), a redirect (the request is sent with `redirect: "manual"` and a 3xx is not followed) or a network error increments `fail_count` and is logged with the push service's host. The 10th failure in a row deletes the subscription (counted in `removed`, not `failed`). Before any of that, a stored endpoint that no longer passes the `POST /api/push/subscribe` endpoint rule (with the current `PUSH_ENDPOINT_HOSTS`) is deleted without a push, counted in `removed` and logged with its host only; the daily cron deletes those too.

### `POST /hooks/ntfy/decide?item&choice&exp&created&ver&sig`

Verifies the signature and expiry (401), then performs the same atomic decide as `POST /api/items/:id/decide` with actor `hook:ntfy`, note `"via ntfy"` and `if_version: ver`. 409 `not_open` when the item is no longer open, or when its `created_at` differs from the signed `created` (deleted and recreated since); 409 `conflict` with `current` when it is still open but its version isn't `ver` (written since the push). 400 `bad_request` when the choice isn't one the item offers (only possible for a hand-made link: the buttons come from the same choices). Manager tokens can't reopen items, so a stale link can't revive through them. Response `{ok: true, status}`.

Links without `ver` (pushed before versions were signed) are refused with 401 `Bad action link`, not honored until they expire: they are exactly the links that could approve content edited after the push, and they lapse within 7 days anyway. The human opens the item instead.

## Data model notes (parity with the artifact)

- Item `status`: `open` → `decided` (human) → `processing` (orchestrator claim) → `archived`. An `open` item also goes straight to `archived` when its asker withdraws it (`decision.choice: "withdrawn"`) or the GitHub hook closes it with its PR (`merged` / `closed`); the UI shows those as "Withdrawn" and "Closed" rather than "Decided". **`decision.ended`** (`withdrawn` | `merged` | `closed`) is how a client tells such an ending from a human's pick: only the server sets it (withdraw and the hook), never a decide, so an item that offers an option with one of those ids still reads right either way. Hook closures from before `ended` existed are recognised by `by: "hook:github"` with `choice` `merged` or `closed`. `auto_decided` items are created `open` with `decision` filled; accept → `archived`; override → `decided`.
- The UI shows `processing` like `decided` ("being handled").
- Default options when an item has none: `proposal` → `approve` / `reject`; every other type → `ack`. Every item also offers `other` (requires a note). `shared/choices.ts` defines them once for the page, the ntfy buttons and decide's validation. ntfy shows at most two buttons and none for an implied `ack`.
- qa roles: `user` renders on the right; `manager` and `orchestrator` on the left (manager messages are labelled with the item's manager id).
- `meta/schedule` is the schedule's source of truth. The UI header reads it; `meta/manager`'s legacy `work_hours`/`timezone`/interval fields are ignored by the UI and mapped into `meta/schedule` by the import script when `meta/schedule` is absent.

## Behavior pinned down during implementation

These fill gaps in the sections above; tests cover each.

- A known path with the wrong method answers 404 `not_found` (not 405). 413 uses code `too_large`; unhandled errors 500 `internal`. A missing `GITHUB_WEBHOOK_SECRET` or `NTFY_ACTION_SECRET` makes its hook answer 503 `unavailable`.
- `PUT` replacing an existing doc keeps the stored `status`, `type` and `created_at` when the body omits them; it drops `snoozed_until` / `snoozed_by` (from before snoozes were per person; see snooze).
- Manager tokens: `status` must be `open` on create and stay as stored afterwards; `decision` must equal the stored one unless the write creates an `auto_decided` item (so a replace of a decided item must carry its decision verbatim, or it gets 403). `source` is fixed once the item exists: a `PUT`/`PATCH` (or answer `data`) that sets it to a different value, or adds one the item didn't have, is 403 `forbidden`; keeping it or dropping it is fine. Otherwise a token could rewrite an orchestrator's `sweep:O3` item to `source: "O3"` and then archive or withdraw a question it never asked.
- **Decided content is frozen** for manager tokens: once an item is `decided`, `processing` or `archived`, a `PUT`, `PATCH` or qa answer `data` from a manager token that adds, changes or removes any field other than `assignee`, `pr_state` (and that only on an item it posted with its own `source`, since `pr_state` is a closure field), `qa_pending`, `qa_last_at`, `qa_answered_at` and `updated_at` is 403 `forbidden` (the message names the fields). That covers the content the human decided on (`title`, `summary`, `question`, `context`, `steps`, `command`, `options`, `recommendation`, `recommended`, `cost_of_waiting`, `evidence`, `links`, `priority`, `type`) and also `source`, `created_at`, `override_of` and unknown extra fields: it is an allowlist, so a field the UI starts showing later is covered too. The legacy `snoozed_until` / `snoozed_by` are exempt: every write drops them (see snooze). `links` count as content (they are what the human saw, and what the GitHub hook matches on); a PR opened after the decision goes on the manager doc (`pr.url`) or through the orchestrator. Answering a question on a decided item still works; only its `data` is limited. A replace must carry the frozen fields verbatim. Orchestrator tokens and humans are not limited (the orchestrator owns the record). Reading another manager's item or qa is 403. `GET /api/orchestrators`, `/api/meta/*` and `/api/lease` are 403; `/api/state` returns `manager: null, lease: null`.
- `POST /api/items/:id/qa` returns 201. Posting a role other than the caller's own is 403. Deciding an `auto_decided` item with anything but `accept`/`override` is 400, as is any other choice the item doesn't offer (decide, above).
- Lease: a write with `X-Lease-Session` from an orchestrator token whose session doesn't hold a fresh lease is 409 `lease_held` with the lease as `current` (`null` when there is none); an empty or over-200-char header is 400. `release` with no lease is 409 `lease_held` with `current: null`; `GET /api/lease` reports `expired: false` when there is none; re-acquire by the same session keeps `acquired_at`, `holder_title` and `holder_url` unless new ones are passed; an `if_version` mismatch is `conflict`, and a fresh lease held by another session is always `lease_held`.
- Change log: deletes carry actor `''` (the trigger can't see the actor). When a filtered feed matches nothing, `cursor` stays at `since`. Deleting an item deletes its qa first, in the same transaction and under the same pin, so the qa deletes are attributed to the item's manager.
- Schedule: pickup slots are the cron firings (UTC minute grid) that fall inside the window; see `cron_exact`. `parseWorkHours` rejects windows that cross local midnight and accepts `24:00` as an end. A stored `meta/schedule` that no longer validates (e.g. an old pickup interval of 7) is served as the defaults, with its `version` and `stored_invalid: true`.
- GitHub hook: the PR URL matches exactly or as a prefix of `/…` and `#…` sub-pages, trailing slash ignored; `pr_state` is set on matching items of any status, unless it is already `merged` (or `closed`, for anything but a merge).
- ntfy: at most 2 `http` actions, the recommended option first; items without explicit options get them only when they are proposals; priority 4 for `high` items.
- People: writes to `users` land in the change log (collection `users`) as `human:<email>`, so they wake `wait --human` like a schedule edit does; deletes carry actor `''`.
- Roles: a blank `ADMIN_EMAILS` (`""`, `" , "`) counts as unset. Emails compare trimmed and lowercased. A decider's `PATCH` (or batch `item.patch`) with any `data` key besides `assignee` is 403, even when the value is unchanged.
- CLI conveniences (not API): `post` creates only (`if_version: 0`) unless `--if-version N`; `wait --human` also matches `hook:ntfy`; exit code 3 for any 409, 4 for a `wait` timeout; `batch` also takes a bare array of ops.
